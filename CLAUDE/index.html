What this is

A static site (Lume 3 + Deno) that publishes chat-archive stats for "The Quartering" Rumble streams. Each stream's stats live as one JSON file in data/; the build turns them into per-stream pages plus a frontpage overview. Deploys to GitHub Pages (kinocoders/jer) via the gh-pages branch on push to main.

Commands

deno task serve         # dev server with live reload (lume -s)
deno task build         # production build into _site/
deno task dev:quality   # deno check && deno fmt — run before committing
deno test               # run all tests
deno test _includes/utils/overview_test.ts   # single test file
deno test --filter "median"                   # single test by name substring
deno task lume <args>   # raw Lume CLI passthrough

DEV=production changes the base path to /jer and enables analytics + the prod site URL. CI sets it; for a local prod-parity build run DEV=production deno task build.

Two-workspace split — the main gotcha

This repo is a Deno workspace with two members that use different JSX runtimes. Getting them confused is the most common mistake.

  • Root (*.page.tsx, _includes/) renders server-side via Lume's ssx runtime (jsxImportSource: "lume"). Use class= not className=, and inject raw HTML through the child object form {{ __html: "..." }} (see _includes/layouts/base.tsx) — not React's dangerouslySetInnerHTML. No hooks, no client state here.
  • app/ (app/components/, app/main.jsx) is client-side React 19 (jsxImportSource: "react", its own app/deno.json with React/ECharts/etc. imports). Standard React: className, hooks, createRoot.

A build-time util in _includes/utils/ may be imported by both sides (it's plain TS), but a component cannot cross the ssx/react boundary.

Architecture

Data pipeline. data/*.json files are the source of truth — each is a full StatsJson (schema v1.3). Adding a stream = drop its JSON into data/; no code change needed. Two page generators walk data/:

  • streams.page.tsx → SSR's a full stream page at /streams/<slug>/ (layout _includes/layouts/stream.tsx).
  • streams-data.page.ts → emits a trimmed /streams/<slug>.json via toClientData() (_includes/utils/client-data.ts), which strips the heavy StatsJson down to what the client islands actually need (events, users, buckets).

index.page.tsx builds the frontpage: groups streams by day and computes the 30-day overview via buildOverviewPoints().

Client islands. Pages SSR a placeholder <div id="island-...">; app/main.jsx is the single bundle entry that hydrates them with createRoot. Mount points:

  • #island-overview-chart (frontpage) → OverviewChart.tsx, reads inline #overview-data JSON.
  • #island-messages + #island-stats-chart-echarts (stream pages) → MessageList.tsx / StatsEcharts.tsx, which fetch the /streams/<slug>.json referenced by <meta name="stream-data">.

main.js is bundled by esbuild (code-splitting on) and only loaded on pages that need it. ECharts is lazy-imported inside the mount.

Shared types. app/types/stats.ts is the type-only single source of truth for the stats schema (constants + StatsJson and friends). Imported across both workspaces. It documents that it's the public schema for chat-stats/*.json produced by an upstream gen-stats.ts (lives in a separate generator repo).

Build-time transforms live in _includes/utils/ as pure, testable functions (overview.ts, client-data.ts, format.ts) and are tested with Deno.test. Keep new derivation logic here rather than inline in components so it can be unit-tested — e.g. OverviewChart delegates its running-median math to overview.ts.

Build-time conventions to respect

  • Prod URL prefix: in production every internal URL is prefixed with /jer by the modifyUrls plugin. Always build internal hrefs/srcs with the url() helper ({ url }: Lume.Helpers), the way stream.tsx and index.page.tsx do — never hardcode /app/main.js.
  • JSON in <script> tags: escape < to < when embedding JSON (e.g. JSON.stringify(x).replaceAll("<", "\\u003c")) so a </script> inside stream data can't break out; the client JSON.parse decodes it.
  • Broken-link gate: _config.ts's check_urls output hook fails the build (Deno.exit(1) on genuinely-broken internal links — it re-checks each against _site to ignore hash-suffixed asset URLs. A failing build here means a real dead link, not a false positive.
  • deno fmt excludes data/**/*.json and CSS; it will reformat ternaries/multiline expressions, so run dev:quality before committing.
